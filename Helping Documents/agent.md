# AGENT.md — VibeTune

## 0. What this file is

Instructions for an AI coding agent (Google Antigravity / Gemini) building **VibeTune**, an ad-free, YouTube-sourced music player. The owner is a **junior / "vibe coder"** developer — write clean, simple, well-commented code, avoid unnecessary abstraction, and explain non-obvious decisions briefly in commit messages or a `walkthrough.md` per phase.

**Use case:** personal / family use for now. The owner may later consider Play Store distribution, which matters for the YouTube-extraction legal posture (see §1.3).

**Constraint that shaped this plan:** the owner has a low-end laptop and cannot run Android Studio or heavy local builds. Every build-heavy step (Android, iOS, desktop packaging) runs in free cloud CI.

**Reference design:** `UI.png` (27-screen mockup — Splash, Onboarding, Login, Home, Library, Songs, Albums, Artists, Playlists, Favorites, Now Playing, Queue, Search, Folders, Lyrics, Equalizer, Sleep Timer, Settings, Theme, Playback Settings, Login User Data, Logout, Lock Screen Controls, Notifications, Sidebar Menu). Match its dark purple/blue gradient aesthetic closely. No exact hex codes/fonts were supplied — extract a palette from `UI.png` and pick a clean sans-serif (Inter, Poppins, or Manrope). Record the result in `design_tokens.md` in Phase W0.

**Reference apps (concept only, no code reuse):**
- SJbuilds04/NOTE — general app structure.
- **Beatbump** — closest match to our architecture (frontend + Cloudflare Workers for YouTube extraction). We use React instead of Svelte.

## 1. Build order (the most important rule)

The project is built **strictly in this order**. Do not start a later stage until the owner approves the earlier one.

1. **WEB** — complete, polished, fully working in a browser (Phases W0–W6).
2. **MOBILE** — only after web is approved (Phases M1–M3).
3. **DESKTOP** — only after mobile is approved (Phases D1–D2). Desktop is a "nice to have": if it proves too painful, the project is still successful without it.

### 1.1 Directories are created only when their stage starts

Do **not** scaffold empty folders for future stages. Create each folder at the moment it is needed.

**Stage: WEB (Phases W0–W6)** — the repo contains only:
```
vibetune/
  AGENT.md
  design_tokens.md
  apps/
    web/                     # React + Vite + TypeScript app (the shared codebase)
  functions/
    youtube-extract/         # Cloudflare Workers project
```

**Stage: MOBILE (Phase M1 onward)** — nothing new at the repo root. Capacitor is added *inside* `apps/web/`, which creates:
```
apps/web/
  capacitor.config.ts
  android/                   # generated by Capacitor (Phase M1)
  ios/                       # generated by Capacitor (Phase M3)
```
> Decision note: Capacitor is the best-documented and least fragile when it lives in the same folder as the web app's `package.json`. Keeping it there avoids dependency-resolution problems between a separate `apps/mobile` folder and the web code. Don't create `apps/mobile`.

**Stage: DESKTOP (Phase D1 onward)** — one new folder:
```
apps/
  desktop/                   # Electron main process + packaging config; loads the built apps/web/dist
```

### 1.2 Structure inside `apps/web/src/` (created in Phase W0/W1)
```
src/
  app/                       # router, providers, theme, app-level state
    layouts/                 # MobileLayout, DesktopLayout, useLayoutMode (see §3)
  core/                      # shared components (buttons, cards, sliders), constants
  platform/                  # thin adapters so shells can swap implementations (see §1.3)
  data/
    models/
    services/                # extraction-api.ts, download-service.ts
    db/                      # storage implementations (IndexedDB now; others later)
    supabase/                # created in Phase W5 only
  features/
    home/ library/ player/ queue/ search/ playlists/ settings/ auth/ ...
```
Rule of thumb: if a junior dev can't find a file in under 10 seconds by guessing its feature name, the structure is too clever.

### 1.3 Platform adapters (so mobile/desktop later is a swap, not a rewrite)
In Phase W2/W3, define small TypeScript **interfaces** in `src/platform/` and give each a web implementation:
- `AudioEngine` (play, pause, seek, setSource, events) → web version uses HTML5 `<audio>` + Media Session API.
- `LocalStore` (get/put/delete/list for songs, playlists, downloads) → web version uses IndexedDB.
- `Platform` info (`isNative`, `isElectron`, `safeAreaInsets`) → web version returns "plain browser".

All feature code talks to these interfaces, never directly to `<audio>` or IndexedDB. In the mobile stage we add Capacitor implementations; in the desktop stage, Electron ones. Keep interfaces small.

## 2. Tech stack (decided)

One React codebase, three "shells" wrapped around it.

| Target | How |
|---|---|
| Web | Plain deployed Vite build — a website |
| Mobile (Android + iOS) | **Capacitor** wraps the same build |
| Desktop (Windows/Mac/Linux) | **Electron** wraps the same build |

| Layer | Choice | Notes |
|---|---|---|
| Frontend | **React + Vite + TypeScript** | Use the `react-ts` template. Single-page app, no SSR needed. |
| Styling | **Tailwind CSS** (or plain CSS modules — agent's call, pick one in W0) | Colors/spacing come from `design_tokens.md` as CSS variables. |
| Mobile shell | **Capacitor** | Real native plugins for background audio + lock-screen controls (a PWA can't do this reliably on iOS). |
| Desktop shell | **Electron** | Chosen over Tauri: no local Rust toolchain, no compile step, biggest tutorial base. Trade-off: heavier download/RAM. |
| YouTube extraction | **Cloudflare Workers** function using an **MIT-licensed** library (e.g. `@distube/ytdl-core`) | Avoid GPL extractors (e.g. NewPipe Extractor) — GPL would force the project to stay open-source forever. In Phase W0, verify the chosen library is still maintained; extraction libraries break often. |
| Local storage | IndexedDB (web) → `@capacitor-community/sqlite` (mobile) → `better-sqlite3` in Electron (desktop) | Swapped behind the `LocalStore` interface. |
| Audio | HTML5 `<audio>` + Media Session (web) → Capacitor native audio plugin (mobile) | Swapped behind the `AudioEngine` interface. |
| Backend (auth/sync) | Supabase (Auth + Postgres) | Wired in Phase W5. |
| State | **Zustand** | Simple for a junior dev to read. |
| Router | React Router | |
| Cloud CI | GitHub Actions (Android, desktop) + Codemagic free tier (iOS) | |

### 2.1 Why YouTube extraction needs a backend
The Node.js libraries (`ytdl-core` and forks) only run in Node — not in a browser or WebView. A small serverless function resolves "YouTube video ID → direct playable audio URL"; the app requests that URL and plays it with a plain `<audio>` element. Build and test this function as its own tiny project first (Phase W0).

**Known limitation:** this can break when YouTube changes something internally. Failures must be **visible error states**, never silent crashes (see §6).

### 2.2 Legal note
This extraction method is against YouTube's Terms of Service. Common and low-risk for personal/family use in the open-source music-client space; **not appropriate for Play Store/App Store distribution** as-is. If plans change later, a different data source or distribution model is needed — revisit then, not now.

## 3. Adaptive layout system (web ↔ mobile app feel)

**Principle:** one theme, two layouts. Colors, fonts, gradients, and components are identical everywhere (all from `design_tokens.md`). What changes is the **layout shell** around the screens. The mobile app must look and behave like a real mobile app, not a shrunken website.

### 3.1 Two layout shells (built in Phase W1)
| | `DesktopLayout` (web on large screens, Electron) | `MobileLayout` (narrow screens, native mobile app) |
|---|---|---|
| Navigation | Permanent **left sidebar** (screen 26, always visible) | **Bottom navigation bar** (5 tabs, taken from `UI.png` — expected: Home, Search, Library, Favorites, Settings; confirm against the mockup) |
| Sidebar Menu (screen 26) | Always open | Slide-in **drawer** opened from a hamburger/profile icon, as in the mockup |
| Player | Persistent **player bar** along the bottom | **Mini-player** floating above the bottom nav; tap to expand to full-screen Now Playing |
| Now Playing (screen 11) | Can be a side panel or full page | Full-screen, swipe-down to collapse |
| Content width | Multi-column grids, hover states | Single column, large touch targets (min 44×44px), no hover-only actions |
| Header | Top bar with wide search field | Compact header, page title, back button |

### 3.2 How the layout is chosen — `useLayoutMode()` in `src/app/layouts/`
Returns `'mobile'` or `'desktop'`, decided in this priority order:
1. **Native Capacitor app** → always `'mobile'` (no override).
2. **Electron app** → always `'desktop'` (set a sensible minimum window size, e.g. 900×600).
3. **Browser** → based on viewport width: **under 768px = `'mobile'`, otherwise `'desktop'`**. It updates live as the window is resized, so the owner can drag the browser narrower and instantly see the mobile app layout during Phase W1.
4. **Browser override:** in Settings, a **"Use desktop layout" toggle** (like "Request desktop site") lets someone on a phone browser force the web/desktop layout. Saved in local storage. Default = automatic.

The router and all screens are the same in both layouts; only the wrapper (`MobileLayout` vs `DesktopLayout`) and a few layout-specific components differ. Screens must not check `window.innerWidth` themselves — they call `useLayoutMode()` or rely on the layout wrapper.

### 3.3 Mobile-app behavior rules (apply to `MobileLayout`)
- Respect **safe areas** (notch, home indicator): use `env(safe-area-inset-*)` padding on the bottom nav, mini-player, and headers.
- Bottom nav stays visible on main tab screens; hide it on full-screen views (Now Playing, Queue, Lyrics, Equalizer).
- Screen transitions feel native: slide for push/pop, slide-up for Now Playing.
- Disable text selection/tap-highlight on UI chrome; use `touch-action` correctly so scrolling is smooth.
- Android **hardware back button** must navigate back (or collapse the player) — wired in Phase M1.
- Set status bar style/color to match the theme (Capacitor `StatusBar` plugin, Phase M1).

### ══ STAGE 1: WEB ══
*Goal: a complete, working music player in a browser, with the mobile-style layout available by narrowing the window.*

### Phase W0 — Setup
- Create `apps/web` with `npm create vite@latest web -- --template react-ts` inside `apps/`. Set up ESLint, Prettier, Git repo.
- Create `functions/youtube-extract/` as its own Cloudflare Workers project. **Test it in isolation** (given a video ID, does it return a working audio URL?) before touching the frontend.
- Install Zustand, React Router, and the styling choice.
- Extract palette + font from `UI.png` → `design_tokens.md`, exposed as CSS variables.
- **Output:** blank themed Home screen via `npm run dev`; extraction function verified with a test request.

### Phase W1 — UI shell (all screens, mock data)
- Build `useLayoutMode`, `DesktopLayout`, and `MobileLayout` first (§3).
- Build all 27 screens with local mock data — no real playback yet. Screens from the mockup that are OS-level (Lock Screen Controls, Notifications) are built as in-app preview/settings screens for now.

- Theme switching (screen 19) working against real app state.
- **Output:** clickable app. Wide window = sidebar + player bar. Narrow window (<768px) = bottom nav + mini-player. Same theme in both.

### Phase W2 — Real playback
- Define `AudioEngine` interface + web implementation (HTML5 `<audio>` + Media Session API).
- Wire frontend to the extraction function for real search + stream resolution (`extraction-api.ts`).
- Real Search (13), Queue (12), Now Playing (11), and mini-player/player bar driven by real state.
- **Output:** search a song and play it in the browser, in both layouts.

### Phase W3 — Local persistence + offline downloads
- Define `LocalStore` interface + IndexedDB implementation: Liked Songs, Playlists, Recently Played, Folders, Favorites.
- Download-for-offline: cache resolved audio locally, prefer local copy when present.
- Library/Songs/Albums/Artists/Playlists/Favorites screens use real local data.
- **Output:** fully usable offline-capable web app.

### Phase W4 — Polish features
- Equalizer (16) — note: Web Audio processing on cross-origin YouTube audio hits CORS restrictions; EQ works reliably on downloaded/cached tracks, may need a fallback for streamed-only tracks.
- Sleep Timer (17), Lyrics (14, source TBD), Folders (15), Playback Settings (20), Notifications (27), Sidebar polish (26).
- **Output:** every screen functional in the browser.

### Phase W5 — Auth + cloud sync (Supabase)
- Create `src/data/supabase/`. Integrate `supabase-js`.
- Login/Signup (3), Login User Data (21), Logout (22) on real Supabase Auth.
- Local-first, sync-on-login for playlists/favorites/history. No complex conflict resolution (personal/family use).

- **Output:** optional account system on web.

### Phase W6 — Web stabilization
- Visible error states when extraction breaks (no silent failures or crashes).
- Performance: list virtualization, image caching.
- Manual test pass of all 27 screens in both layouts; deploy the web build (Cloudflare Pages or similar).
- **Output:** ✅ **Web approved.** Only now may Stage 2 begin.

## 5. Definition of "done" for every screen
- Works in `DesktopLayout` **and** `MobileLayout` (from Phase W1 onward).
- Uses only theme tokens (no hard-coded colors).
- Has loading, empty, and error states.
- Reachable via navigation; no dead ends.

## 6. Working agreement for the agent

- Follow the stage order in §1. **Never scaffold or install anything for a later stage early.**
- Work one phase at a time. End each phase with `npm run lint`, `npm run build`, any tests, and a `walkthrough.md`.
- **Stop at every checkpoint** and wait for the owner's go-ahead. Don't auto-continue.
- Small, scoped commits — no giant multi-feature commits.
- Extraction failures show a visible error state (with a retry), never fail silently or crash.
- Readable, commented code over clever code.
- If `UI.png` and this file disagree (e.g. the exact bottom-nav tabs), follow `UI.png` and note the choice in the phase's `walkthrough.md`.
